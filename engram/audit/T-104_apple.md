## 1. Resumen ejecutivo

1. **El flujo de `main` es correcto frente a los requisitos publicados de Apple para notarizar:** firma con Developer ID (requisito explícito), hardened runtime solo en el ejecutable principal, secure timestamp en cada firma y en el DMG, sin `get-task-allow`, entitlements en XML válido (`xmllint` en `release_mac.sh:109`), orden zip→notarize→staple(.app)→DMG→firmar con `-i`→notarize→staple→`spctl`/`hdiutil verify` (`release_mac.sh:250-276`). Coincide punto por punto con «Notarizing macOS software before distribution» y «Customizing the notarization workflow».
2. **Probado hoy con identidad real (no ad-hoc):** el tramo de firma del script, replicado literal sobre una copia del bundle con «Apple Development» + `--options runtime` + `--timestamp`, firma los ~150 Mach-O en 68 s, deja `flags=runtime` solo en el .app y `flags=none` en dylibs/frameworks, pasa `codesign --verify --deep --strict`, el chequeo de Team ID del script da 0 errores, `syspolicy_check distribution` solo reclama el ticket (esperable sin notarizar) y la app **arranca y sigue viva a los 18 s** cargando FFmpeg 9.0.1. Cierra la deuda D-28 «hardened runtime con cert real no verificado» en lo que se puede verificar sin Developer ID.
3. **De los 20 hallazgos de T-086: 16 CERRADOS, 2 PARCIALES (APP-02 cuenta Apple sin certificado ni API key; APP-13 README OK pero sin prueba en Mac limpia), 1 ABIERTO por decisión del PO (APP-20 Windows sin firma, T-101), 1 N/A por diseño (APP-06 → dos builds thin, ADR-005 §5).**
4. **El primer release real hoy aborta en el gate D-14:** `DISCLAIMER.md` conserva 5 marcadores `[A DEFINIR POR EL PO` (líneas 147, 163, 174-176); el `--dry-run` lo imprime y `release_mac.sh:90-100` corta el build en las dos patas del workflow. Es el primer paso del checklist (§4).
5. **Del lado de GitHub no hay nada configurado todavía** (`gh api`: 0 environments, 0 rulesets, 0 secrets, 0 releases). Sin el environment `release` + regla de tag `v*` + 5 secrets + ruleset de tags, el tag `v1.0.0` falla cerrado en «Exigir firma y notarización» (`release.yml:136-147`): no sale un DMG ad-hoc por error, pero tampoco sale release.
6. **Riesgo 14.4-14.7 (D-15) acotado:** sonda con `vtool` muestra que dyld de macOS 14 **no rechaza** una dylib con `minos` mayor al SO (cargó una con `minos 99.0`); la compatibilidad de los 12 bindings `minos 26.0` depende solo de símbolos, y entre 14.4 y 14.8 no cambia la API pública. El mínimo lo imponen los frameworks de Qt (`minos 14.4`) y Launch Services vía `LSMinimumSystemVersion`. Sigue sin prueba empírica en 14.4-14.7 (§6).
7. **CI: el Python de `actions/setup-python` es el pkg oficial de python.org (`python-3.14.8-macos11.pkg`), universal2, `minos 10.15` (x86_64) / `11.0` (arm64)**: PyInstaller con `target_arch=None` extrae la rebanada nativa (doc PyInstaller) y el minos-check (`release_mac.sh:163-191`) pasa. numpy resuelve a `macosx_14_0_{arm64,x86_64}` con los hashes del lock. No veo un fallo previsible del build en CI fuera de D-14 y la config de GitHub.
8. Hallazgos nuevos: **0 bloqueantes nuevos, 1 Alta (APP-21: gate D-14 + GitHub sin configurar = el tag no produce release; ya conocido como deuda, lo elevo a orden del día), 3 Medias, 4 Bajas.** Ninguno requiere código antes del tag salvo que el PO lo decida (APP-24 Rosetta/README, APP-26 `cancel-in-progress`).
9. Mac App Store (T-102): nada cambió en lo estructural desde T-086 §8 salvo que QtVirtualKeyboard (GPL-only) ya no viaja (T-096). Sigue siendo 3-5 días (sandbox + bookmarks vía PyObjC, quitar Ko-fi y updates, LGPL). No recomendado para 1.0.

### 3.2 Verificado y OK (sin hallazgo)

- **Requisitos de notarización de Apple** (Context7, «Notarizing macOS software before distribution → Prepare your software»): código firmado en todos los ejecutables (`release_mac.sh:202-216`), certificado Developer ID Application (nunca ad-hoc/Apple Development: el script lo recibe por `DEVELOPER_ID`, el workflow lo extrae del `.p12` con `find-identity` `release.yml:107-113`), hardened runtime en el target de app (`:199,215`), secure timestamp (`:198,206,211,215,266`), sin `get-task-allow` (`grep` vacío en `entitlements.plist`), SDK ≥ 10.9 (bootloader SDK 14.5), entitlements XML válidos (`xmllint`).
- **Notarización con API key** (TN3147): `notarytool … --issuer --key-id --key` no necesita Apple ID; `store-credentials --key … --keychain <temporal>` en `release.yml:126-128` y `--keychain` en submit/log (`release_mac.sh:77-78,236-240`).
- **Salida de `notarytool submit --wait`:** la doc muestra exactamente `id: …` y `status: Accepted`, que es lo que parsea `release_mac.sh:238,243`.
- **Frontera de secrets** (GitHub Docs «Deployments and environments»): «Secrets stored in an environment are only available to workflow jobs that reference the environment»; la regla de tag «is matched against the GITHUB_REF»; un environment inexistente se crea sin reglas ni secrets → en ese caso el fail-closed de `release.yml:136-147` aborta. Environment secrets y deployment rules están disponibles en repos **públicos** con GitHub Free (el repo es público: `gh repo view` → PUBLIC).
- **PyInstaller con Python universal2 en CI:** «By default, PyInstaller targets the current running architecture and produces a single-arch binary» y «extracts the corresponding arch slice from any collected fat binaries, including the bootloader» (feature notes). Con `target_arch=None` (`rb_exporter.spec:98`) cada pata sale thin; `release_mac.sh:290` lo imprime (`lipo -archs`).
- **`LSMinimumSystemVersion` como mecanismo de bloqueo**: Apple (Information Property List) lo define como la versión mínima requerida para ejecutar la app en macOS; la release note de Big Sur 11.0.1 confirma que las apps «must honor» ese valor. Es lo que ve el usuario de 14.0-14.3 (diálogo del sistema, no crash).
- **Entitlement único**: `com.apple.security.cs.allow-unsigned-executable-memory` es una excepción documentada del hardened runtime y la notarización la acepta (T-086 citó «Hardened Runtime»); reconfirmado hoy en la práctica (arranque OK).
- **Icono**: `icon.icns` existe en el repo y en `Contents/Resources` (bundle viejo); `CFBundleIconFile` en el plist.

## 5. Mac App Store: qué cambiaría (actualiza T-086 §8, para T-102)

Sin novedades estructurales; lo que cambió desde T-086 y lo que sigue igual, con cita:

| Tema | Estado hoy | Impacto |
|---|---|---|
| App Sandbox obligatorio | Apple («Preparing your app for distribution»): «If you distribute your macOS app through the App Store, you must enable App Sandbox. If you notarize … you must enable hardened runtime and can optionally enable App Sandbox». | Hoy solo hardened runtime. Sandbox exige mover `settings.ini`/`rekordbox_fixes.json`/logs al container (transparente para `app_paths.py`) y cambia todos los accesos a disco |
| Acceso a archivos | `com.apple.security.files.user-selected.read-write` + bookmarks app-scope; cada acceso a una URL con alcance de seguridad requiere `startAccessingSecurityScopedResource` / `stop…` balanceados (Apple, NSURL). | Las rutas que vienen **dentro** del XML/NML (miles de pistas que el usuario nunca eligió una por una) y `traktor_db.py:325,340` (`~/Documents/Native Instruments`) requieren que el usuario conceda la carpeta raíz y persistir un bookmark; en Python hace falta PyObjC. Es el cambio grande (3-5 días) |
| Ko-fi | Sigue en `ui.py:100,169-200` (URL, QR y botón «invitarme un café»). | Quitar o pasar a IAP de propina en el build MAS (T-086 §8 citó la guideline 3.1.1/3.2.2) |
| Chequeo de updates | `update_checker.py` + toggle `check_updates_on_start` (`ui.py:320,1186`). | Deshabilitar en el build MAS (guideline 2.4.5(vii), citada en T-086) |
| `subprocess` `pgrep` para detectar Traktor | `traktor_relocate.py:149`. | Dentro del sandbox, **no verificado** si `pgrep` ve procesos ajenos |
| QtVirtualKeyboard (GPL-only) | **Ya no viaja** (`rb_exporter.spec:55-57`, `check_bundle.sh:12-14`, T-096). | Un obstáculo menos |
| LGPL (Qt, FFmpeg) | `THIRD_PARTY_NOTICES.md:20-21,37-54`; bundle sellado + sandbox dificulta el relink del usuario; Qt pide `-feature-appstore-compliant` (T-086 citó Qt for macOS). | Riesgo legal, no de App Review; sin cambios |

| Privacidad | Nutrition labels + URL de política de privacidad (T-086). | Una página |

## 6. Qué no se pudo verificar (me abstengo)

- **Notarización real** con Developer ID (no hay certificado en la cuenta): todo lo anterior es firma con «Apple Development», mismo mecanismo de hardened runtime pero distinto tipo de certificado; Apple rechaza ese tipo en el notary, por eso no se intentó enviar.
- **Arranque en macOS 14.4-14.7** (D-15): sin máquina/VM. La sonda dyld reduce el riesgo a «símbolo ausente», no lo elimina.
- **Pata arm64**: sin Mac Apple Silicon; la evidencia es la resolución del lock (`macosx_14_0_arm64`), el Python universal2 de python.org y la doc de PyInstaller sobre thinning.
- **Comportamiento del bundle nuevo** (post-T-096/T-103): no se buildeó (instrucción del PO); se infiere del spec, de los tests y del `--dry-run`. El bundle viejo difiere en `LSMinimumSystemVersion` (14.0) y en los frameworks QtQml/QtQuick/QtVirtualKeyboard que ya no viajan.
- **Error 65 de `stapler`** (APP-23): sin fuente primaria de Apple.
- **`syspolicy_check` y versión de Xcode/`notarytool` en los runners `macos-15`**: no verificado.
- **Rol mínimo de la API key** (Developer vs Admin) para notarizar: RELEASE.md:84 ya lo marca sin doc primaria; no encontré una hoy.
- **Config real de GitHub una vez creada** (environment, regla, ruleset): hoy no existe; QA deberá verificarla con `gh api` cuando el PO la cree (§4 pasos 4-5).
- **Gatekeeper en macOS 15/26 con la app notarizada**: sin Mac con esas versiones; la doc de Apple (Technology Overviews → Distribution) dice que con ticket Gatekeeper verifica y muestra el diálogo informativo de primera apertura.
